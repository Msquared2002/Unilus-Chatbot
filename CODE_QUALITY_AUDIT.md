## 3. CSS audit

- Production widget and dummy-site styles are predominantly external CSS files. Inline styling is concentrated in developer tools: embedded `<style>` blocks in `campus-survey.html`, `campus-survey-review.html`, and `routing-editor.html`; inline style attributes in `campus-survey.html` and `routing-editor.html`.
- Large stylesheets include `chatbot-widget/widget.css` (1,016 lines), `chatbot-widget/avatar.css` (436), and `css/website.css` (631). They need clear component section headings and a selector-use pass supported by rendered-page checks.
- Colors and spacing recur across the widget and the demo-site CSS. A shared variable scheme could improve consistency, but globally consolidating values risks changing visual appearance. Keep tokens scoped to existing design surfaces and consolidate only after visual review.
- The separate `3d-prototype` has its own preview CSS and should remain isolated from production widget styles.
- No CSS rules were removed or moved in this audit because there is no CSS coverage or browser screenshot baseline to prove visual equivalence.

## 4. Naming consistency findings

- Naming mixes camelCase JS modules with hyphenated static page and asset names. This is conventional for their respective uses; do not rename without checking references and deployment paths.
- Backend modules mix `require('fs')` and `require('node:fs')`; standardizing built-in module imports is a safe future cleanup, but no bulk formatting was applied.
- The two `*_before_navigation.js` names imply snapshots but live alongside runtime source. Clarify their archival status before moving/removing them.
- JSON uses domain-specific snake_case in generated/data contracts and camelCase in JS. Preserve those external data contracts; normalize only internal identifiers when a focused change warrants it.
- No filename, function, or JSON field was renamed.

## 7. Risks identified

- Archived-looking files may support undocumented manual workflows; verify ownership before removal.
- Generated bundle and ZIP tracking may be intentional for static deployment or hand-off.
- CSS edits need browser-level visual review; text-only checks cannot establish equivalent layout.
- Supabase integration should connect behind current service/data access seams and retain existing response contracts; no schema or provider assumption was made.
- The checkout had a large set of pre-existing modifications and untracked files. Those were intentionally preserved.
